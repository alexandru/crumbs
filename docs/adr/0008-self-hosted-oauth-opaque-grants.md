# Use self-hosted OAuth with opaque, atomic grants

Crumbs runs its own OAuth authorization server for REST and MCP access. Users are local accounts managed through the CLI and Rust API. Client authorization uses dynamic client registration, authorization code with PKCE S256, and explicit consent on every grant; Crumbs does not keep a remembered browser login. Public and confidential clients are supported. Client metadata is untrusted, and redirect URIs are validated when registered and when used. Crumbs intentionally omits fetching Client ID Metadata Documents (CIMD). The current MCP specification recommends CIMD support with `SHOULD` and permits Dynamic Client Registration (DCR) as a compatibility path with `MAY`. Crumbs chooses DCR to avoid fetching client-controlled URLs and the associated server-side request forgery (SSRF) surface; clients must use DCR.

Crumbs generates random authorization codes and bearer tokens, stores only their SHA-256 digests, and persists sessions in the database. Code redemption, refresh-token rotation, replay handling, and user-wide revocation are transactional. Replaying a redeemed code or a rotated refresh token revokes its session family. This stateful design makes revocation immediate and avoids a JWT signing secret; it requires database-backed session checks. User password changes, deactivation, and deletion revoke sessions and outstanding grants.

REST and MCP tokens use distinct resource audiences. The `crumbs:read` scope permits search and custom-food reads; `crumbs:write` permits custom-food creation, replacement, and deletion. Grants may include either or both scopes, and omitted scopes default to read access. Each MCP tool call enforces the permissions of its own authenticated HTTP request. Deployments terminate TLS at a reverse proxy and configure the externally visible issuer origin. Rate limits are held in process memory and remain local to that server process.
