# Store self-contained profile logs with query projections

Journal entries extend the shared log model with independent, nonblank free text. They use the same profile ownership, occurrence day and time, editing, deletion, and pagination rules. The single entry-type filter includes `journal`; omitting it returns all entry types. See the [profile log API](../profile-logs.md).

Supported entry types are defined by the Rust and API models. The database extracts the type for queries but does not keep a separate list of allowed type names. New log categories do not require a schema change just to permit their names.

Authenticated users own profiles with stable IDs; there is no default profile, and names are unique within a user after ignoring case and surrounding whitespace. Profiles support create, update, and list, with no deletion. Logs support create, update, delete, and list through Rust, REST, and MCP APIs. A shared profile-log table stores a self-describing JSON union for food, biometric, and journal entries; only weight biometrics are initially supported. Query columns carry the owning profile ID, required occurrence date, resolved occurrence time, entry type, biometric subtype, optional source reference, and UTC creation and update timestamps. Metadata must agree with the payload but is not required to deserialize it.

Occurrence time is optional on input and defaults to the current local clock time in the profile timezone, including for backdated entries; the resolved local time is stored. A profile's timezone defaults to UTC. Occurrence values are independent of UTC persistence timestamps. Queries require the owning profile and support optional inclusive date bounds, entry type and biometric subtype filters, descending ID order, and last-ID pagination with `id < last_id`; there is no direction parameter. A source reference is stored, but there is no source-reference query API.

Food-log requests require a valid local `FoodId`, positive fixed-point `amount`, and `serving_size`. Crumbs validates the food and serving: mass foods accept compatible mass units and named servings, while volume foods accept compatible volume units and named servings; no implicit mass-to-volume conversion is performed. Missing usable calorie data is rejected with an actionable message advising the agent to edit the food or create a new food; zero calories is valid. The snapshot records measured quantity, total calories, all available nutrient values with units and qualifiers, description, optional `FoodId`, and the amount and serving-size input, including a named serving count when supplied. It uses existing fixed-point quantity and nutrient component types in a dedicated consumed-total representation, separate from per-100 g or per-100 ml nutrition profiles. The API requires `FoodId`, while stored JSON permits it to be absent.

REST edits use PATCH, with equivalent partial updates in Rust and MCP; omitted fields are preserved. Date or time edits preserve the food snapshot. Explicit changes to `FoodId`, amount, or serving size rebuild the snapshot from food data. Changes or deletion of source foods never alter or delete log snapshots. There is no revision history. Creating, updating, or deleting a weight entry atomically recalculates cached current weight using occurrence day descending, occurrence time descending, `created_at` descending, then ID descending; if no weight remains, the cache is null. The design duplicates query metadata and food snapshots to support efficient reads and stable history.
